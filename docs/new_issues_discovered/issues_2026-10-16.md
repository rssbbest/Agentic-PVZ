## Unity ⇄ SDK/backend contract

Compared `autopilot-game-engine/Assets/Scripts/NetworkManager.cs` and
`docs/docs_by_developers/backend API guide.md` with the backend and SDK code.
Rule: the Unity build trusts every reply, so the SDK/backend must only send what
the guide allows. "Verified" = reproduced against the backend code.

### Which Unity script is current?

The latest networking script is `unity-files/Assets/Scripts/NetworkManager.cs`
(provided by the user). `autopilot-game-engine/Assets/Scripts/NetworkManager.cs`
is an older copy (only `/api/team` and `/api/results`, no `sessionID`/`coins`)
and should not be used as the reference.

What the latest script does:
- URLs: `getTeamDataUrl`, `pushResultsUrl`, `pushReinforcementsUrl`,
  `pushScreenshotUrl`, `pushGameStateUrl`, all defaulting to `http://127.0.0.1:5000/api/...`.
  **No login URL and no `Authorization` header anywhere.**
- `/api/team`: body from `JsonUtility.ToJson({teamID})`; reply read into
  `TeamDataResponse {sessionID, coins (int), defencePlacementData, enemies {enemyId, count, allowedRows}}`;
  the raw reply is kept as `SpawnSettingsJson`/`GameSettingsJson` for other
  scripts (spawner, GameManager) to read `spawnSettings`/`gameSettings`.
- `/api/results`, `/api/reinforcements`, `/api/state`, `/api/screenshot`: 3
  attempts, `timeoutSeconds = 10` each, 2 s realtime wait between them, retry
  only on `ConnectionError` (which includes a timeout); any HTTP error status is
  final. The reinforcement reply body is handed to a callback in another script
  (not seen), so how `placeDefences`/`coins`/`defencePlacementData` are parsed is
  not visible here.

### Confirmed by the Unity developers (2026-10-16)

- Unit positions in snapshots are whole numbers within (0,0)-(10,5) → #2 is not an issue.
- `coins` in the reinforcement reply is an `int` field: send `0`, never `null` → #13 must be fixed.
- build7 reads `spawnSettings.spawnSequence`, with the rules in the API guide
  ("Spawn sequence") → #1/#17 are real.

### Requests (Unity → SDK/backend)

| # | Issue | Effect |
|---|---|---|
| 10 | **No login in Unity (confirmed in the latest script).** The SDK and backend expect the game to send `POST /api/login` (SDK messages say "log in on the game page") | Eval started from the game always gets 401 `Log in with your team ID and password first`, which the player cannot do in the game; they must log in through the SDK (`--team`, console `L`). No `llmToken` arrives, so agent LLM calls fail at the gateway unless `AUTOPILOT_GATEWAY_KEY` is set by hand. `REQUIRE_LOGIN=true` would block every game. Without a login the typed team ID is trusted, so anyone can `play` as any team. Options: make the SDK login the required step (and fix its messages), or add a login screen and URL to Unity |
| 11 | **Timeouts don't fit (confirmed in the latest script).** `PushCaptureRoutine` gives each reinforcement attempt 10 s and retries on timeout (3 attempts, ~34 s). The SDK gives the agent up to 10 s, plus worker start-up and up to 1.5 s for the referee. (In WebGL the request goes through the browser's Fetch API; assumed to honour the timeout, as the API guide's ~34 s implies) | A slow agent makes Unity resend the identical snapshot: the SDK runs the agent again (a retried opening becomes `phase="pause"` without `upcomingEnemies`); placements the referee approved for the abandoned attempt are charged and counted in the score but never placed; after 3 tries the game shows "No response from agent". Fix direction: keep agent + referee well under 10 s (e.g. agent limit ~7 s), and/or make the SDK recognise a retry (same `sessionID` + `elapsedSeconds`) and answer it with the first decision. `/api/results` has the same 10 s vs 10 s race (SDK forward timeout is also 10 s), which can cause duplicate posts (backend keeps the first) |
| 12 | ~~`/api/team` body built without escaping; short-ID check sends anyway~~ | **Fixed in the latest script** (`JsonUtility.ToJson`, `yield break`) |
| 21 | Unity side: with `DEBUG_MODE` on, the team, results and reinforcement URLs are taken from the UI boxes with no fallback when a box is empty (the known build7 "fill the three URL boxes" issue, `docs/issues/build7-empty-url-boxes.md`). Screenshot and state URLs are not overridable | An empty box means that call fails; screenshot/state always go to `127.0.0.1:5000` even if the other boxes point elsewhere. For the Unity developers |

### Checked and matching

Snapshot fields (`teamID`, `sessionID`, `elapsedSeconds`, `counts`, `defences`,
`enemies`), result fields, placement and enemy shapes, unit type names (match the
cost table), `coins` meaning (balance after the decision), `defenceId` 0-3,
grid 11×6. Against the latest script: `/api/team` request body, `sessionID`
(string) and `coins` (always an int in `/api/team`), `enemies[].allowedRows`
(list of ints), screenshot multipart fields (`screenshot`, `teamID`,
`sessionID`) and the `/api/state` body all match what the backend accepts.
